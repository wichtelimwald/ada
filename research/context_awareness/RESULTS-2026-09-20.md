## Redundancy implications

A strict dual-consensus policy would unnecessarily block common valid inputs because dateparser disagrees with quickadd on core German appointment expressions.

Run 1 therefore favors further evaluation of:

1. **quickadd primary + typed semantic validation**, with another resolver as shadow/fallback;
2. **selective consensus** only for classes where two independent resolvers are known to have comparable semantics;
3. **degraded single-resolver mode** for characterized low-risk/unambiguous classes.

Agreement is evidence, not proof.

## Maintenance / security observation

Quickadd's runtime behavior fits Ada's temporal use case very well, but the current fork has limited recent code maintenance and loads its bundled Naive Bayes model through Python pickle during module import.

This is not automatically a hard-gate failure because the dependency is pinned and local, but it is a material security/maintenance concern:

- unsafe deserialization is part of normal import;
- the model is a binary/opaque artifact;
- adoption would require an explicit supply-chain/hardening decision.

Notably, dateparser 1.4.0 removed its own import-time pickle loading specifically to avoid unsafe deserialization of packaged data.

## Next characterization step

Before choosing a resolver:

1. enrich the dateparser adapter with parser-period/granularity metadata so type mismatches can fail safely instead of appearing as valid datetime conflicts;
2. test whether a reasonable, library-native dateparser configuration materially improves the three failed cases without Ada-owned parsing rules;
3. evaluate quickadd with a safe scorer/model-loading strategy or determine the cost of patching/replacing pickle loading;
4. measure parse/startup latency and dependency footprint;
5. then complete the weighted decision matrix.
